## 3. 稿子约定（每位写稿人必须遵守）

### 3.1 线框记法

- 一律用 ``` 包裹的 **ASCII 框线**，**左边距 0**，框内宽度 ≤ 100 字符（便于 diff 与终端阅读）。
- 框内**只写结构与文案位**（`[按钮]`、`(输入)`、`▸` 折叠、`⋯` 更多），**不写颜色值、不写 px**。
- 需要标注尺寸/栅格时，用**语义尺寸**：`卡高≈2行`、`栅格 2×2`、`正文区 maxHeight≈10行（内滚）`——具体像素留 UI 阶段。
- 每张线框下方必须紧跟一行 **「线框说明」**，逐条解释图中编号（`①…`）对应的组件与行为。
- 响应式只要求两个断点：**宽（≥1100，默认）** 与 **窄（<1100，单列堆叠）**；窄屏只画一次最简形态。

### 3.2 组件树记法

用缩进列表（不是 ASCII），每个节点一行：`- 组件名（DSH 原语 | 自研）— 职责 / 关键 props / 数据来源`。

- **DSH 原语**指 DSH 前端链已提供的组件或槽位（按钮 / 输入 / 弹窗 / 折叠 / Tag / 卡片外壳 / 列表 / 空态 / 骨架屏 / 审批卡…）。**点名到原语族即可，不写 import 路径**（那是实现票的事）；无法确认可用性的，写「(需确认)」并在该屏末尾登记到「待验证」。
- **自研**指 xuanshu-client 要自己写的组件，命名用 `Xs` 前缀 + PascalCase（如 `XsOverviewGrid`、`XsConsultPuPicker`）。
- 每个组件节点必须能对上**槽位**或**父组件**；不允许出现无归属节点。

### 3.3 交互流程记法

- 编号步骤 `1. → 2. → …`，每步写清：**触发**（谁点的什么 / 哪个事件）→ **系统做什么**（宿主 API、文件落盘、LLM 调用）→ **界面变成什么**（状态名）。
- 凡涉及**写盘、调用 LLM、调 horosa、开新会话**的步骤，必须标 `【副作用】` 并写明写到哪里（`~/.dsh/xuanshu/...` / 会话 meta / `ctx.schedule`）。
- 凡涉及**人会改到自己的东西**的步骤，必须标 `【人工确认闸门】`。
- 状态名一律用同一套稳定名：`empty` / `loading` / `ready` / `error` / `running` / `done` / `stale`（陈旧）——在同一屏内复用，不新造同义词。

### 3.4 关键状态（验收硬要求）

每屏**必须**给出 `空态`、`加载态`、`错误态` 三种；按该屏实际情况**追加** `只读态`、`禁用态`、`陈旧态`、`超预算态`、`并发/中断态`、`窄屏态`。

**空态必须可执行**：写清「为什么是空的」+「下一步按钮」+「指向哪」（可跳转的槽位或票号）。只写「暂无数据」视为不合格。

### 3.5 复制即用的页头（每屏文件开头必须有）

```md
# S<n> · <界面名>

> 归属票：<07/08/…> ｜ 层级：<main 面板 / 抽屉 / 会话内区块 / 设置内页> ｜ 槽位：<见 shared/DSH槽位映射.md 的键名>
> 上游依据：`docs/specs/001-assembly-foundation.md` §<…>；`docs/architecture-v1.md` §<…>；<若有> `.scratch/assembly-foundation/issues/<票>.md`
> 规格级复用来源：<星阙八字录入 / 挂载账本 / Best-of-N / 无>
> 本屏不做什么：<一句边界>
```

### 3.6 每屏的固定小节（顺序不可变，缺一节即不合格）

1. `## 1. 目的与入口`（从哪进、去哪出、与哪些屏相邻）
2. `## 2. 线框`（宽/窄两态）
3. `## 3. 线框说明`（编号逐条）
4. `## 4. 组件树`（含槽位归属）
5. `## 5. 交互流程`（编号 + 副作用/确认闸门标注）
6. `## 6. 关键状态`（空/加载/错误 + 追加态）
7. `## 7. 规格级复用来源`（表：交互点 → 星阙出处（文件:行）→ 复用/偏离 + 偏离理由）
8. `## 8. DSH 槽位实现映射`（表：屏内部位 → 槽名 / 宿主 API / main key）
9. `## 9. 硬约束在 UI 上的呈现`（按 §5 勾选相关条目并写清「界面上怎么让人看出来」）
10. `## 10. 素材需求`（表：id → 类型 → 用在哪 → 建议格式）
11. `## 11. 验收自检`（对照本屏归属票的 checklist 逐条打勾，并写「怎么验」）

## 4. 硬约束：在 UI 上必须看见（票 02 验收项 3）

以下是产品铁律，**不能只写在文档里**——每一屏都要把它们变成可见的界面事实。写稿时按 §5 的映射勾选，并在该屏第 9 节给出**具体文案与控件**（不是「加个提示」这种空话）。

| # | 约束 | 出处 | 界面上必须呈现为 |
|---|---|---|---|
| C1 | **命盘卡只读** | 铁律 2 / 用户故事 11 | 卡内无任何编辑控件；详情抽屉顶部一枚「只读 · 由出生信息与底座生成」标记；唯一写操作是「重新录制出生信息」（跳 S3，且二次确认） |
| C2 | **底稿只读（纯派生）** | 产品定义 #4 / 用户故事 25 | 底稿视图无编辑入口；顶部「纯派生 · 不可手改」标记 + 「要改就改源头」三个跳转（谱 / 工作区 / 工作流）；唯一按钮是「刷新」 |
| C3 | **藏不可见 AI** | ADR-0003 / 铁律 4 | 藏库顶部常驻一行「藏永不进 AI：只登记指针、签与跳转，玄枢不读、不索引、不分析」；藏卡片上无任何 AI 动作（无摘要、无问答、无「让 AI 看看」） |

| C5 | **底座与底稿默认在场、不可关** | 用户故事 14 | 勾选谱列表里这两项以**锁定行**呈现（无 checkbox，标「默认在场 · 不可关」），与可勾选谱在视觉与语义上分组 |

| C8 | **是否跑通由人判定** | 产品定义 #2 | 工作流向导里**没有**系统的「通过/失败」判定；只有人点的「导出 skill」按钮 + 一句「跑没跑通由你判定」 |

## 6. 本稿做出的定案（把「留到 UI 阶段」的项收口）

以下三项此前登记为待定，票 02 即「UI 阶段」，**在此定案**，下游按此实现（实现票若发现不可行，回改本稿而非就地偏离）：

| # | 定案 | 依据 / 理由 |
|---|---|---|
| D1 | **管理入口落位 = 侧栏 `sidebar.panellist` 分区**：「家」（自我总览）/「书房」（问事）/「库」（谱 / 藏 / 底稿）/「流水线」（工作流）；**设置菜单只放系统项**（模型 / 审批 / skill / MCP / 定时任务） | 原「设置菜单 vs 左上角入口条」二选一（产品定义 #13）。选侧栏分区：与 DSH 既有的 `sidebar.panellist` 机制同构（加性 list 槽，零框架改动，符合 ADR-0001）；设置菜单里塞「谱」会把信息型系统伪装成配置项，与 CONTEXT 的「谱是信息、不是能力」相抵。**工作区/项目不在此分区**，走 DSH 原侧栏 |
| D2 | **四卡既有空态又有骨架屏**：首屏 `loading` 用**卡级骨架**（每卡各自骨架，不整页转圈），**不做全屏 loading** | 四卡数据来源与耗时不同（命盘=本地文件、日课=当日产物、底稿=派生文件、快捷入口=静态），整页 loading 会让最快的卡等最慢的卡 |
| D3 | **窄屏（<1100）单列堆叠顺序**：命盘 → 日课 → 底稿 → 快捷入口 | 与「我是谁 → 今天注意什么 → 我的汇总 → 去哪」的读序一致 |
