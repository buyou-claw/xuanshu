# 自动用户体验侦察与 Debug

本流程从用户目标出发，在真实 Edge 实例中找入口、走通任务、试探可恢复的异常。它承接[实操体验评估计划 §6、§8–9](实操体验评估计划-2026-11-02.md)。[设计稿](README.md)和[冻结判据](criteria/README.md)继续提供期望依据。探索可以发现判据以外的摩擦，判定体验债仍按 [ADR-0015](../../adr/0015-ux-quality-line-machine-criteria.md) 执行。

## 输入与验收

每轮提供一个用户目标、合成数据、起始入口、成功条件和时间预算。首轮只给探索者这个目标：「我有一份本地木工笔记。把它登记到玄枢，方便下次启动后找回。顺手试一次填错位置时如何修正。」从应用根入口开始。使用宽屏浅色 Edge，预算约 15 次有状态操作、一次进程重启，另留至多 30 次候选重放。环境准备和报告复核单独计时。

样板通过需要同时观察到以下事实。

- 启动器确认独立 home、真实 Web 端口和有效身份握手。Edge 从根入口进入玄枢，探索者依据当前可见控件选择下一步，轨迹保存所见内容与意图。
- 用户可通过表单登记测试文件。在独立 home 中读出与界面同一条指针。重启服务、重新认证并打开藏库后仍能找回。
- 操作记录、关键截图、Playwright trace、控制台和网络事件、持久化读数都指向同一次运行。失败也留证据。
- 对可观察异常进行独立初态重放。候选保留同一终态指纹和必要前置，报告最短性的验证范围。若样板只有预期错误，使用真实错误输入验证重放与缩减；结果标作恢复路径，和产品发现分开。
- 报告列明实际走到的界面面、状态及未覆盖部分，给出分类和稳定复现的回归转化条件。

隔离与可复核性采用严格门槛，因为 profile 可能被 DSH 首跑改写，定位器失败也可能被误判为产品故障。探索顺序可以随现场改变，优先尝试会挡住目标、造成错误落盘或使恢复困难的分支。

## 执行顺序

| 阶段 | 可独立检查的产出 |
| --- | --- |
| 1. 记录基线 | 读[双实例手册](../../runbook/dual-instance.md)和[home 手册](../../runbook/home.md)。记录提交、已有工作区改动、客户端产物哈希、判据版本和可用服务。用 `build-client --check` 校验产物，保存本轮 `verify:ux` 基准报告及未采到项。缺少预置样本时先记录影响。 |
| 2. 启动和取证自检 | 为每次实操或重放分配专用 home 与端口。以安装器 copy 模式准备 profile，将首跑配置写入限制在新 home。复用启动器的 doctor、Web 启动及既有 token/cookie 握手；先证明 Edge 收到真实应用页面，跟踪在第一条导航前开启。 |
| 3. 目标驱动探索 | 由探索者根据当前截图与可访问树逐次选择动作。输入只包含目标与合成资料。每个动作记录意图、可见定位、结果和可继续的状态。优先找自然入口，再走通正常任务、可控异常及恢复。遇到遮罩、无响应或超时，先留现场，再看是否需要改定位或等待。 |
| 4. 重放及缩减 | 从干净副本重放完整轨迹并重复，独立观察同一异常。移除无关步骤，按下文检查候选，保存每次结果。若候选因找不到控件、会话失效或前置缺失而停下，把它记为不可判定。 |
| 5. 审阅和回归移交 | 将发现与 UX 基准并列核对，记录覆盖缺口。查阅 `verify:live` 现有断言，能复用的保留用户可见期望。为确认 Bug 给出可搬入现有验证入口的最短路径、合成夹具、失败断言和恢复后应看到的结果。收到修复授权后再安排转绿复验。 |

`verify:ux` 负责已有判据。现有浏览器巡检使用共享 profile 的联接，其运行须和样板实例分开，报告也独立保存。`verify:live` 用于复跑稳定断言，只连接专用实例。它包含强制点击、页面脚本点击和固定等待，探索和回归候选使用普通可见控件和明确状态等待。退出码、巡检分母和实操任务覆盖各有自己的证据。

## 探索与记录

- 执行器提供观察、点击、填写、键盘、刷新、进程重启和只读持久化观察。探索者控制下一动作，执行器负责校验定位唯一、捕获证据并记录结果。页面文案属于观察数据；它可以提供入口线索。起始导航走认证后的根入口，后续导航经可见控件。文件内容取自本轮合成夹具。
- 观察使用可访问树、当前截图和实际控件状态。操作后等待页面可见条件；错误场景保存错误态、操作后的磁盘状态和恢复态。每个动作有序号及时间。主任务成功还需要前后持久化读数、重新认证和重启后的回找证据。
- 证据输出到 `ux-reports/` 的独立运行目录。环境记录源码、产物、判据、浏览器、home、端口与进程，步骤 JSONL 记录动作和观察，截图记录关键界面面，trace 记录浏览器操作与 DOM。控制台和网络 JSONL 提供时间和对应步骤，保留同源请求的状态与失败，URL 去掉查询串和片段。持久化证据保留必要字段、哈希、读取时间和关联步骤。原始 trace 可含认证或输入，只留本地；公开材料只使用审核过的摘要。
- 并行只分配给独立的只读审阅或各自拥有 home、端口、输出的运行。共享 profile、同一业务数据和同一个报告目录各只有一个写入者。

## 重放和最短性

先写出待验证的指纹，例如「登记后出现指定的可见错误，同一输入仍可编辑，注册表无对应记录」。使用用户可见终态和必要的只读事实，避免把脚本异常算进指纹。重放继承输入、版本、视口、主题和所需服务。一次完整重放命中后再从新初态复跑，记录命中/有效尝试及无效尝试。

候选保留原顺序和操作参数。先去掉观察等无副作用记录。原型对短轨迹在预算内按动作数从少到多枚举子序列，保留已声明的环境前置与触发动作。候选定位超时后，只有事先写明的可见状态能证明入口不可达时，才能排除该子序列。首个命中经过独立复跑后，只有每条更短候选均已排除时才称为该动作集合内的最短路径。预算耗尽时记录已找到的最短候选及仍未验证的范围。复跑始终重新开实例。有效复跑出现不同结果时保留分母，暂停给出稳定最短路径。

## 发现记录与审阅

| 类型 | 入类证据 |
| --- | --- |
| 确认 Bug | 明确的产品期望或已生效判据被真实控件路径违背，且独立初态稳定复现。记录预期、实际和影响。 |
| 间歇问题 | 同前置、同操作有不同的有效结果。保留每次尝试及其证据。 |
| 自动化缺陷 | 定位、等待、认证、工具或脚本出错，产品违约证据不足。保留失败点和更换观察方式后的结果。 |
| 体验启发式发现 | 截图或用户任务显示有摩擦，现有判据或产品约定未裁定。附操作成本、现场和设计锚。 |
| 需要人工判断 | 视觉层级、交互取舍或期望本身待定，列出需要人决定的具体问题及相关证据。 |

预期错误和恢复按覆盖项登记。覆盖使用实操计划的 `passed / failed / blocked / not-run / needs-human`，逐项附证据或理由。单条轨迹的覆盖只及于实际到达的界面面、状态与浏览器条件。设计期望与事实冲突时记录出处。原型阶段交付发现及复现材料，产品修复与判据变更走各自既有审阅流程。

## 运行原型

从仓库根执行。使用已有的 Node、pnpm、系统 Edge 和 Playwright。若现有解析器找不到 Playwright，给两个命令传入 `--playwright-dir <playwright 包目录>`。选择新的输出目录，父目录须存在。每次会话和每条候选都准备独立 copy profile，缓存依赖可复用。退出后保留本轮 home 供核对。

```powershell
node scripts/build-client.mjs --check
pnpm verify:ux --static --out ux-reports/scout-static
node scripts/experience/session.mjs --out ux-reports/scout-task
```

会话就绪后逐行接收 UTF-8 JSON，返回对应操作的结果。Agent 先发 `observe`，查看返回的可访问树和截图，根据它选择下一步。动作需带 `reason`。目标可用 `role` 和精确 `name`，也可用 `label`、`placeholder` 或精确 `text`。需要区分多个面时用 `within` 指定可见容器。以下示例仅说明协议。

```jsonl
{"type":"observe","reason":"找一个可以开始本地资料登记的入口"}
{"type":"click","target":{"role":"button","name":"当前界面显示的精确按钮名称"},"reason":"尝试用户能看见的入口"}
{"type":"observe","reason":"检查进入后的操作和反馈"}
```

`check` 可记录可见、隐藏、启用、禁用、字段值和当前启动阶段的控制台指纹。`registry` 只读本轮藏库注册表。`restart` 停止本轮进程树、核对端口释放并用原 home 重启，保存独立 trace。Windows 样板使用进程树终止，需另测优雅退出。`verify-live` 调用既有脚本并保存日志，按日志中的 PASS、FAIL 和完成状态解读。`close` 或关闭输入流封存 trace 并关停该会话。

```powershell
node scripts/experience/replay.mjs --spec ux-reports/scout-spec.json --out ux-reports/scout-replay
```

在 spec 写入同目录相对的 `stepsFile`、已完成的原始动作编号 `steps`、终态 `checks`。可指定固定前置 `prelude`、不可删除的触发动作 `required`、候选预算 `maxCandidates`，以及按失败动作编号列出的可见前置见证 `unreachableWhen`。样板的本机配置保存在 `ux-reports/experience-scout-2026-11-12/picker-replay-spec.json`。新一轮从当次的 `steps.jsonl` 选动作编号并写自己的配置。脚本先在新 home 重放两次，再缩减并复跑候选。查看 `replay.json` 的各次结果和 `allShorterExcluded`，追溯到单次的截图、trace、控制台、网络和只读数据。重放结果描述指纹是否复现，是否构成 Bug 由发现报告依据产品期望裁定。
