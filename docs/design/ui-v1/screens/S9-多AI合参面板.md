## 1. 目的与入口

- **从哪进（双触发，二者等价）**：① **conversation 面板的原生 composer** 里输入 `/多模型 <问题>` 发送；② composer 上沿 / 会话内区块上的「多 AI 合参」按钮（未带问题时，先弹一行输入框问「这一轮要合参的问题是？」）。**命令名照抄上游**：`/多模型`（主，`utils/aiChat/commands.js:28`；票 11 与 `docs/specs/001-assembly-foundation.md:72` 已把这两个字钉死）＋ 玄枢别名 `/合参` ＋ 上游别名 `bestof`；**产品功能名一律写「多 AI 合参」**，界面文案不出现「多模型对比」（那只是第 7 节里的上游实现名）。（注：`shared/星阙交互规格索引.md` §3.3 D21 的「命令改名为 `/合参`」建议已被 lead 收口否决，**该索引行需回改**。）
- **渲染面（README §6.4 D5）**：本区块**不挂在 `consult` 面板下**（该面板没有会话绑定）；它注册在 DSH `conversation` 面板的会话绑定子槽里，用户「进入会话」的动作即 `ctx.layout.selectPanel(null)`（D6）。
- **开关**：设置里「多 AI 合参」默认**关**（用户故事 18「平时轻量、需要时再开」）；关闭时按钮与命令都在，触发时先提示一次并给「去设置打开」。
- **去哪出**：S6（采用 / 合并 / 否决后回到会话流，本轮变成一条 assistant 消息）；S7（历史回看只带采用稿）；S8（候选截断护栏与挂载预算同口径）；S10（会话结束后的沉淀）。
- **相邻屏**：S6、S7、S8、S10、设置（模型 / 合参开关）。

## 2. 线框

### 2.1 宽（≥1100，默认）· 触发（命令 + 按钮 + 费用确认）

```
┌ DSH 会话面板 · 问事会话 #consult-0007 ───────────────────────────────────
│ ① composer：[ /多模型 这次转岗该不该去                          ][发送]
│    ⓘ 也可点右侧按钮触发；首版 2 路：经典派 + 审慎派（同一模型两视角）
│ ② 多 AI 合参 · 预估费用确认
│    候选 2 路 · 视角 经典 / 审慎 · 模型 <当前模型>        ⓘ 费用未知
│    ⓘ 合参候选只回答、不执行任何动作（不带工具、不读写你的文件）
│    [开始合参]   [改视角 / 换模型 ▸ 设置]   [取消]
└──────────────────────────────────────────────────────────────────────────
```

**线框说明**：① 命令式触发——首字符 `/` 且第二字符非 `/` 才算命令，命令名到第一个空白为止、其余为问题原文（与上游解析规则一致，`utils/aiChat/commands.js:60-69`）；按钮式触发是等价入口；**触发面是 DSH conversation 面板的原生 composer**（`consult` 面板不自绘输入区，README §6.4 D5）。触发前一行常量说明「首版 2 路 = 经典 + 审慎」。② 费用确认框——上游有价表给金额、无价表给「费用未知」**但仍要确认**（`components/aianalysis/chat/useChatAssist.js:266-269`）；玄枢照此，并把「候选只回答、不执行动作」写在框内（D23：玄枢的会话默认带全套工具，不写清会被误以为候选能动手）。

### 2.2 宽 · 2 路并排（生成中 → 判官给出排序）

```
┌ 多 AI 合参 · 2 路 ────────────────────────────────────────── [停止全部] ──
│ ① ┌ c1 · 经典派            ┐  ┌ c2 · 审慎派            ┐
│    │ Tag 排序 1 · 生成中…    │  │ Tag 生成中…             │
│    │ …（流式正文，内滚）     │  │ …（流式正文，内滚）     │
│    └────────────────────────┘  └────────────────────────┘
├──────────────────────────────────────────────────────────────────────────
│ ② 判官（只排序，不替你做决定）
│    c1  8 分 · 依据充分、自洽      ← 排序理由，不是「建议采用」
│    c2  6 分 · 覆盖够但结论偏保守
│    ⓘ 判官只看候选与问题，不读你的谱与挂载内容
│ ③ [采用 c1] [采用 c2]   [合并为一稿]   [否决本轮]      ⓘ 判官不会自动采用
└──────────────────────────────────────────────────────────────────────────
```

**线框说明**：① 候选卡并排（列数 = `min(候选数, 2)`，4 路时 2×2；**首版 2 路**）：每卡含候选 id Tag、视角/模型名、判官得分 Tag（有该 id 的理由才显示，排名第一给显式标记）、状态位（`生成中` / `失败` / `{N} 字`，后面按有值才追加 ` · {x.x}s`、` · ${cost}`）、正文内滚区。**生成中卡片底部只有「停止全部」一枚**，不出现采用/合并/否决。② judge 区：只给**排序 + 每候选 1–10 分 + 理由**，标题行固定写「只排序，不替你做决定」，**没有任何**「建议采用 / 自动采用」控件或文案（C9）；第二行小字披露 **H4**（判官不读挂载与谱）。③ 三动作（生成结束且有 ≥1 份有效候选时才出现）：`[采用 x]` 按候选各一枚 + `[合并为一稿]`（≥2 份有效候选才可用）+ `[否决本轮]`。

### 2.3 宽 · 判官失败回落（排序按完成顺序）

```
┌ 多 AI 合参 · 2 路 · 判官不可用 ───────────────────────────────────────────
│ ① ⚠ 判官不可用，暂按先完成的一份排前（判官未给出有效排序：解析失败 / 请求失败）
│    这只影响排序展示，不替你选 —— 采用与否仍然由你点。
│    [就这么选：从下面两份里点一份采用]        [合并为一稿]      [否决本轮]
│ ②  c1 · 经典派   Tag 完成顺序第 1 · 8 字/无分     [采用]
│     c2 · 审慎派   Tag 完成顺序第 2               [采用]
└──────────────────────────────────────────────────────────────────────────
```

**线框说明**：① 回落必须**在界面上可解释**：一句人话（「判官不可用，暂按先完成的一份排前」）+ 效力边界（只影响排序展示、不替你选）+ 三条出路（自己点一份采用 / 合并 / 否决）；② 候选卡 Tag 从「排序第 1」换成「完成顺序第 1」，把「这不是判官结论」写进标签本身；③ **本屏没有「重跑判官」按钮**（上游 `rejudge` 在玄枢 v1 不做，README §6.1）。上游原文的警示行是「判官未给出有效结果,已按完成顺序采用第一份」（`components/aianalysis/chat/BestOfCards.js:42-48`）——玄枢**偏离**这半句，因为 C9 不允许把「回落排序」写成「已采用」。

### 2.5 宽 · 否决本轮（玄枢自有语义，定案 D4）

```
┌ 多 AI 合参 · 2 路 · 已否决 ─────────────────────────────── [▸ 展开候选] ──
│ ① 本轮合参作废：没有任何一份被采用（adoptedId 为空），也不会进入后续对话与历史回看
│    ⓘ 候选正文仍保存在本地会话记录里（candidates），可展开、可导出
│    [重来一轮（沿用同一个问题）]
└──────────────────────────────────────────────────────────────────────────
```

**线框说明**：① 否决的后果必须写明三件：不采用任何候选、`bestOf.adoptedId = null` + `bestOf.rejected = true`、**历史不带任何候选正文**；同时写明数据没丢（候选仍在 `message.candidates` 里，可展开可导出）；`[重来一轮]` 是常用出路。否决**不跑判官、不调合并槽**。上游**没有**「否决」按钮（只有采用/合并/停止全部，`useChatBestOf.js:93-152`）——这是玄枢自有语义，界面文案不得写成「停止」。

## 5. 交互流程

1. **触发**：触发 = `/多模型 <问题>` 命令（别名 `/合参` · `bestof`）或 点「多 AI 合参」按钮 → 系统解析问题原文（命令名到第一个空白为界；`//` 开头不算命令）；若是按钮且未带问题，先弹一行输入框 → 界面 `ready`（费用确认框）。三条守卫照抄：空问题 → 「写上要合参的问题」并不发送；主发送进行中 → 「正在生成，稍后再试」；无可用模型 → 「请先选择可用模型」。
2. **拦截引导（玄枢加严）**：触发 = 本次既无勾选可选谱、也无挂载项 → 界面弹 §2.6 引导（结构照上游、文案换玄枢措辞）；选择「只带底座 + 底稿合参一次」则继续，否则不发请求。
3. **费用确认**：触发 = `[开始合参]` →【副作用】无（尚未调用）；界面进入 `running`。取消 → 回到会话，不产生任何消息。
4. **并行候选生成（旁路，H3）**：系统按当前设置起 N 路（首版 2 路：经典 / 审慎；视角以**首条 system 消息末尾追加**「【本候选视角】directive」的方式注入）→ 各路口独立流式写回自己的候选卡；候选流**不带 tools / toolChoice、不挂结构化输出**，共享一个中断开关 → 界面 `running`（每卡独立状态：生成中 / 失败 / `{N} 字 · {x.x}s · ${cost}`）。**H3**：本过程**不写**主会话的挂载账本、字数状态与工具调用轨迹；主发送可与之并行（提示「会与它并行进行」）。
5. **判官**：触发 = ≥2 份候选有效 →【副作用】无写盘；系统发一次**短的非流式**调用（超时 60s），系统词标记「判官」，按「**依据充分、自洽 > 覆盖充分 > 表达清楚**」给 1–10 分与理由，输出严格结构化（`best` / `ranking` / `reasons`）→ 界面 `ready`：候选卡按排序打 Tag（排名第一给显式标记），judge 区列出分数与理由。**H4**：判官请求**不带挂载数据**（只喂问题前段 + 各候选正文），界面以 §2.2 ② 的小字披露。
6. **判官失败回落**：触发 = 解析失败 / 请求异常 / 超时 →【副作用】无；系统把排序置为**完成顺序**（先写完的在前），judge 记录错误标记 → 界面显示 §2.3 的解释；**不自动采用任何一份**（C9），也**不提供重跑判官**（v1 不做）。
7. **采用**：触发 = 点某张候选卡的 `[采用]` → 系统把该候选正文写成本轮消息内容，`bestOf.adoptedId = 该候选 id`，其余候选保留在 `message.candidates` → 界面 `done`（§2.4 折叠摘要）。落库失败不阻断显示（照抄上游）。
8. **合并**：触发 = `[合并为一稿]`（**要求 ≥2 份有效候选**，不足时按钮禁用并提示「可合并的候选不足两份」）→ 系统走终稿槽发一次合并调用（总编语义：以排名靠前为主干、吸收有依据的补充、去重、矛盾处以有依据者为准并注明、**不新增候选里没有的事实**；超时 120s）→ 合并稿作为 `id:'merged'` 追加进 `candidates`（已有 `merged` 则只更新其正文），`bestOf.adoptedId = 'merged'`，记 `mergedBy` → 界面 `done`（提示「已合并为一稿并采用」）。
9. **否决（玄枢自有语义，D4）**：触发 = `[否决本轮]` →【副作用】无；**不跑判官、不调合并槽**；`bestOf.adoptedId = null`、`bestOf.rejected = true`，候选全部折叠保留在 `message.candidates` → 界面 §2.5；**历史不带任何候选正文**（后续对话与 S7 回看都不带）。
10. **停止全部（生成中）**：触发 = `[停止全部]` → abort 共享控制器（同步、不发请求）；已产出的文字保留并标「已停止」；**不跑判官、不自动采用任何一份**，界面进入「已停止」中间态等人点采用 / 合并 / 否决。
11. **记录结构**（规格，落在会话 JSONL 的消息上）：`message.candidates = [{id, label, model, angle, text, status, error?, usage?, elapsedMs?, costUsd?}]`；`message.bestOf = {adoptedId, ranking, judge, costUsd}`（`judge = {model, reasons, error?, skipped?}`；合并时追加 `mergedBy`；否决时 `adoptedId = null` + `rejected = true`）。顶层 `usage` = 被采用候选的 usage（合并时 = 合并稿）。
12. **历史只带采用稿**：触发 = S6 后续对话装配历史 / S7 打开回看 → 系统只取 `adoptedId` 对应的内容（`'merged'` 也在内）；**否决轮次不带任何候选正文** → 界面（S7）只渲染采用稿。
13. **与主发送并发**：触发 = 合参生成中又发主消息 → 主发送**照常进行**，界面提示「本次发送会与它并行进行（互不占用发送门闩）」（照抄上游）。
14. **设置**：触发 = 设置里打开 / 关闭「多 AI 合参」→ 关闭后命令与按钮仍可见，触发时提示「先去设置打开」；已发生的合参轮次不受影响。

## 6. 关键状态

> **状态词表声明（README §3.3）**：本屏是**流式**区块，通用 `loading` 由 `running`（生成中）承担——`empty` = 等待费用确认、`ready` = 已具备可拍板条件、`running` = 生成中、`done` = 已采用/已合并、`error` = 各类失败。另有两个本屏专有中间态：「已停止」「已否决态」（§6.1 D4）。

| 状态 | 什么时候 | 界面是什么样（可执行） |
|---|---|---|
| `empty` | 区块刚挂上、等待费用确认 | 触发说明行 + 费用确认框；`[开始合参]` / `[取消]`；不占讨论区 |
| `running`（生成中，可中断） | 候选并行流式中 / 合并请求中 | 每卡独立状态；区块右上 `[停止全部]`；**生成中卡片底部不出现采用/合并/否决**；`[停止全部]` 后进入「已停止」中间态 |
| 「已停止」中间态 | 人按了停止全部 | 显示已产出的候选（有文字者标「已停止」）+ `[采用某份]` / `[合并为一稿]`（≥2 份时）/ `[否决本轮]`；**不自动采用**（与上游「取首个有文字候选」自动回落**偏离**，理由：C9） |
| `ready` | ≥2 份候选有效、判官已回 | 候选按排序打 Tag + judge 区（分数 + 理由 + 「只排序」句 + H4 披露句）；三动作可用 |
| `done` | 已采用 / 已合并 | 折叠摘要行（`多 AI 合参 N 份` Tag + `采用:X` + `· 判官 {model}` + `[▸ 展开候选]`）+ 采用稿正文 |
| 已否决态 | 点过 `[否决本轮]` | §2.5 摘要行；明写 `adoptedId` 为空、不进历史；`[▸ 展开候选]` 可看候选、`[重来一轮]` 可重跑 |
| `error` | ①全部候选失败 ②部分失败 ③合并失败 ④判官不可用（回落） | ①整块 error：`[重试合参]` + `[退回普通问法（带工具）]` + 一行可能原因（模型不可用 / 未配置）；②失败卡保留卡位 + 失败原因原文 + `[只重跑这一路]`，有效卡照常可采用（**1 份 → 不跑判官**，直接进「只有一份可用」中间态，`judge.skipped = true`）；③合并失败：「合并稿为空」/超时 + `[直接采用某一份]`；④回落态见 §2.3。另：结构化短调用拿到**空正文**时，系统会去掉结构化约束原样重发一次（第三级降级，`utils/aiStructuredOutput.js:111-133`）——界面此时保持 `running`，不闪错误 |
| 拦截引导态 | 本次无勾选可选谱、无挂载项 | §2.6 弹框：标题 + 两条去路 + 单按钮 + 不发送；保留「只带底座 + 底稿合参一次」的显式出口 |
| 禁用态 | 设置关闭；或可用视角 / 模型不足 2 路 | 关闭 → 「多 AI 合参当前是关的，去设置打开」；不足 2 路 → 「合参需要至少两路：去设置加一个视角或换用不同模型的候选」，给 `[去设置]` 与 `[照常问（带工具）]`；**不静默降级成 1 路** |
| 窄屏态 | <1100 | §2.8：单列候选、三动作固定底部 |
