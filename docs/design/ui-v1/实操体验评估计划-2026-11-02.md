# 玄枢实操体验评估计划

日期：2026-11-02

状态：评估范围、任务驱动方法及后续收敛流程的讨论记录，尚未开展本轮实操评估。

本轮授权：先记录文档；环境准备、模拟使用和修复不在本次执行范围内。

## 1. 评估目标

以一个逻辑完整、体验统一、能够长期使用的成熟个人桌面应用为目标。可用、易懂、美观都是基本要求，全部纳入评估；优先级只用于安排后续修复顺序。

重点是现有界面的完成质量与基础交互细节，包括美观、按钮与跳转逻辑、输入输出冗余、操作反馈、状态一致性和实际使用中的 BUG。通过实际模拟用户使用形成结论，源码用于后续定位原因，不能代替实操证据。

### 1.1 当前阶段与推进单位

现阶段以现有功能的产品收敛为重点。进入执行阶段后，每轮先选定要完善的使用任务，暂停向该轮追加无关新功能，避免范围不断扩张。本文不据此认定当前各项功能已真实可用。

以一条完整用户任务作为评估和验收单位：从入口、输入、动作、等待与反馈，一直到结果、离开和再次找回。功能票完成、单元测试通过、静态巡检转绿分别提供工程证据，不能单独证明这条任务易懂、顺畅或美观。

AI 应主动探索任务内的实际入口与适用状态、发现并归纳问题，不要求用户逐个口述。用户集中判断具体的视觉样板与需要取舍的方案；未被既有规则覆盖的主观发现保留证据，不由 AI 自行改动冻结判据。

## 2. 已确定的范围与边界

| 议题 | 用户确定的口径 |
|---|---|
| 产品目标 | 完善的产品，功能闭环、容易理解和 UI 美观都是基本要求 |
| 整体布局 | 保持当前主要区域、导航结构和功能归属 |
| 局部调整 | 允许建议合并重复按钮、精简重复提示、已有信息自动带入、收敛重复展示 |
| 视觉方向 | 以当前界面与设计语言为基准评估精细度，本轮不另选视觉风格 |
| 评估方法 | 实际操作运行中的产品，沿完整任务观察输入、动作、跳转、反馈和结果 |
| 测试环境 | 独立体验环境，使用虚构测试数据，走真实功能 |
| 真实验证缺口 | 无法真实完成的环节明确登记，不能凭源码、历史测试或模拟响应认定通过 |
| 阶段产出 | 有证据的问题记录、局部优化建议、修复优先级与复测方法 |

讨论中的早期“可调整布局”选项已被用户后续要求收紧，以本表的固定整体布局、允许局部精简为准。首页重新组织、产品概念重构和更换视觉风格不属于本轮方案。

## 3. 重点检查维度

| 维度 | 实际检查内容 |
|---|---|
| 美观与精细度 | 对齐、间距、字体层级、颜色、边框、图标、按钮尺寸是否协调；长文本、真实结果和错误提示出现后是否挤压、截断或溢出 |
| 按钮与跳转 | 名称与实际动作是否一致；点击后是否到达预期位置；返回落点是否合理；是否丢失输入、选择和原来的浏览位置 |
| 输入合理性 | 是否重复填写已有信息；默认值是否合适；必填、格式与限制是否清楚；错误提示能否定位到具体输入项并帮助修正 |
| 输出清晰度与冗余 | 结果是否容易找到、重点是否清楚；同一内容或状态是否无必要地重复展示；结果与提示是否矛盾；是否暴露了妨碍理解的技术信息 |
| 操作反馈与恢复 | 操作后是否有响应；等待、成功、失败是否容易区分；连续点击是否重复提交；取消、中断或失败后能否继续 |
| 一致性与闭环 | 同类按钮、文案、弹窗和操作是否保持相同习惯；保存后能否找回；再次进入或重启后状态与数据是否符合预期 |

同一信息出现多次不自动判为冗余。需要结合所在任务判断：必要的提交前复核、摘要与详情、来源说明或人工确认可以保留；记录重复的实际用途和造成的负担后，再提出局部精简建议。

## 4. 计划覆盖的用户任务

执行时先对照实际可用功能确认入口，再逐条走通。下表是任务计划，不表示已经执行或发现缺陷。

| 任务 | 计划观察的闭环 |
|---|---|
| 首次设置 | 从空状态理解下一步，填写出生信息与相关配置，检查校验、前后步骤衔接、保存和后续入口 |
| 自我总览 | 理解当前状态，从卡片进入相关内容，查看结果，再返回原位置；检查摘要、详情与提示的重复或矛盾 |
| 谱管理 | 创建、填写、保存、查看、编辑、搜索与再次打开，检查重复输入、状态反馈和内容保留 |
| 问事与历史回看 | 选择谱、开始问事、提交、等待、查看结果、离开与找回，再继续使用 |
| 临时挂载与多 AI 合参 | 进入配置、理解选择、开始、查看过程与结果、停止及失败恢复；检查按钮去向和状态衔接 |
| 会话沉淀 | 从结果进入草稿、复核、人工确认写谱，再查看保存后的内容；保留人工确认边界 |
| 日课、晚省、底稿与事记 | 进入、查看内容和生成状态，理解时间与来源，使用适用的更新入口，离开后再回看 |
| 藏库与工作流 | 登记或创建、查看、跳转或试跑、返回、再次进入；检查本地指针与实际结果的反馈 |
| 相关设置与桌面操作 | 在任务涉及的位置检查配置入口、数据备份、窗口关闭后再打开等行为；无法运行桌面壳的项目单独登记缺口 |

任务经过 DSH 原生界面时，记录与玄枢的衔接问题及其归属。此项不扩大为上游全部界面的独立重设计，也不默认要求修改上游。

每条任务覆盖实际适用的状态：首次使用、日常使用、空数据、加载、成功、错误输入、失败、取消和操作中断。对可保存的任务检查离开后再进入、重启后回看；不对不适用的功能强套状态。

### 4.1 首条样板路径（建议，执行时核实）

建议先沿“自我总览 → 选择谱 → 开始问事 → 查看结果 → 离开 → 从历史找回并继续”建立样板路径。先确认真实入口及 AI 配置、谱等前置；首次设置或谱创建若是必要前置，应纳入关联任务，不能绕过界面补数据后宣称整条路径通过。

这条路径用于集中观察入口辨识、重复信息、等待反馈、返回落点、结果保留与视觉一致性。它是首轮建议，不代表已走通，也不缩减 §4 的最终覆盖范围。服务受阻时，继续评估独立可走的任务，同时保留该路径的验证缺口。

## 5. 执行方法

1. 记录执行日期、源码版本、运行实例、实际加载的客户端产物、窗口尺寸、主题及服务可用性，固定本轮可比较的环境。
2. 使用独立体验 home 和明确标识的虚构数据，避免混入日常使用数据。环境准备本身不算用户体验验证完成。
3. 从真实界面入口开始操作，记录用户目标、输入、动作、跳转、反馈和结果。不通过直接调用内部 API 或修改数据文件绕过界面步骤来宣称任务通过。
4. 先走正常任务，再补测适用的错误输入、连续点击、取消、返回修改、切换界面和重启继续等路径。涉及等待时，同时观察中间反馈和最终结果。
5. 功能判断以实际运行结果为依据；视觉判断结合真实内容、截图和既有设计要求。自动化可以辅助点击与采集，静态检查与单元测试用于补充，不能取代本轮实操。
6. 遇到异常时先保留操作与界面证据，再读取相关源码定位；复现步骤与原因推断分别记录。
7. 缺少 AI 配置、horosa 或桌面壳等前置时，记录阻塞点、已走到的步骤及尚未验证的部分。使用替代响应的演示只能说明界面状态，不能作为真实服务闭环通过的证据。

本轮实操评估会在独立测试数据上产生必要的创建、保存与更新，以检查完整闭环。它不同于 ADR-0015 所述的只读 UX 巡检，不改变该巡检的只读边界，也不赋予日常数据写入权限。

### 5.1 从评估到收敛的分阶段循环

| 阶段 | 执行内容 | 阶段交付 |
|---|---|---|
| 确定本轮任务 | 固定任务、环境、边界和完成条件，暂缓无关功能扩展 | 本轮范围与前置记录 |
| 主动实操 | 从真实入口走正常与适用异常路径，先取证再定位 | 操作记录、截图、可复现发现与阻塞 |
| 归并发现 | 按共性原因或待验证的原因假设关联多个现象，按用户影响排序 | 发现清单、关联记录与建议批次 |
| 提出样板建议 | 在既有布局、设计语言内，对首条路径提出具体局部改法 | 带位置、预期效果及复测方法的方案 |
| 实施小批修复 | 进入修复阶段后，每批围绕一个相关主题修改 | 范围明确的改动与验证证据 |
| 原路复测与扩展 | 重走原步骤、检查相邻入口，将已确认的处理方式用于后续任务 | 前后对照、剩余缺口与下一轮任务 |

本次只更新计划。环境准备、主动实操、原型制作和代码修复均不因本表而自动开始；后续按用户指定阶段执行。

### 5.2 共性问题归并与样板使用

- **保留现象，验证原因**：同类保存反馈、返回行为或控件表现可以关联归并，但相似现象不等于同一根因。原因未证实时标为假设，每条原始发现仍保留自己的复现步骤与证据。
- **按主题小批推进**：例如统一已确认有问题的保存反馈、修正相关返回落点、收敛同类按钮样式。避免一批同时扩大为导航重组、产品概念调整和大面积视觉重做。
- **样板覆盖完整状态**：首条路径的样板同时考虑标题层级、间距、按钮主次、表单反馈、真实长文本、空态、加载态和失败态，不能只展示一张理想成功截图。
- **样板服从设计权威**：使用既有 token 与界面稿；具体样板用于呈现执行效果，不成为第二套设计规范。与设计稿冲突或需要新增判据的内容，走 §8 指向的既有流程。
- **确认后再推广**：需人工判断的视觉取舍集中呈现具体前后效果与理由。后续任务复用已确认的处理方式时，仍检查其实际适用性和相邻路径，不机械复制。

## 6. 问题记录格式

每项发现至少记录：

| 字段 | 内容 |
|---|---|
| 标识与位置 | 稳定的记录编号、任务名、界面面及入口 |
| 环境与前置 | 版本、实例、窗口条件、数据状态和服务条件 |
| 用户目标 | 这一步实际想完成什么 |
| 操作步骤 | 输入、点击、等待、跳转和返回等可复现步骤 |
| 预期表现 | 依据产品语义或既有设计，用户应该看到什么 |
| 实际表现 | 实际看到什么、是否成功、是否出现重复或矛盾 |
| 证据 | 截图及其关联步骤；必要时补充操作记录和脱敏日志 |
| 影响与优先级 | 阻断、误导、重复操作、阅读负担或视觉不协调的具体影响 |
| 规则关联 | 已有判据及出处，或明确标记为待人工判断、判据缺口 |
| 发现性质与关联 | 已复现缺陷、交互负担、视觉发现或判据缺口；关联发现编号、共性原因或待验证假设、建议批次 |
| 局部建议 | 保持整体布局的具体改法，以及需要保留的必要信息 |
| 复测方法 | 修复后如何沿原步骤检查结果，以及相邻入口是否受影响 |
| 验证状态 | 已复现、未稳定复现、待人工判断或受环境阻塞 |

实操证据只支持其实际覆盖的路径和状态。一张静态截图不能证明跳转、保存或重启后的行为正确。

## 7. 排序与报告要求

按用户影响安排后续修复顺序：

- **优先处理**：无法继续任务、输入或数据丢失、保存与实际结果不一致、错误结果或错误跳转。
- **随后处理**：状态误导、返回后重做、重复输入、无必要的重复展示，以及明显增加操作成本的问题。
- **持续完善**：对齐、间距、字阶、图标、边框、控件一致性等视觉细节。严重影响辨识或操作的视觉问题按实际影响提升优先级。

最终报告包括任务覆盖记录、问题与证据清单、共性原因与假设、局部优化建议、首条样板路径方案、建议修复批次和未验证项。任务覆盖记录逐项写明路径、状态、证据和是否受阻，发现数量减少不能代替覆盖完成。全部质量维度都要交代，不以一个总分或测试通过数替代完整结论。

后续若进入修复阶段，应保留修复前证据，修后沿原步骤复测，并检查相邻路径。报告生成与具体修复是不同阶段；本次仅记录计划。

### 7.1 后续修复批次的完成条件

每批开始前固定所处理的发现编号、影响路径和预期变化。批次完成需同时说明：

- 原始问题沿原步骤复测的结果，以及相邻入口、输入保留、结果找回和适用异常恢复是否受影响。
- 视觉变化在可比较的窗口、主题和数据条件下的前后证据；需要人工判断的项目明确保留判断状态。
- 受影响测试与工程检查的实际结果，遵循仓库验证要求；代码变更交付前运行 `pnpm verify:all`，分别报告测试和工程检查。UX 修复说明、判据权威与转绿验证遵循[判据目录说明](criteria/README.md#4-变更权与修复通道)，不以更新截图基线、放宽阈值或减少采集范围替代修复。
- 未通过、未采到、无法复现及受环境阻塞的项目逐项说明归属和下一步，不能记为完成。

样板路径只有在已选范围内的任务可完成、适用异常可恢复、交互与视觉有对应证据后，才报告该范围完成；仍待人工判断或受阻的部分明确列出。每轮完成一条路径或一个相关修复主题，再扩大到后续任务；不以“全部看过一次”或一个总分作为产品完成条件。

## 8. 与既有设计及工程约定的关系

- 本文是实操评估的范围与方法记录，不新增设计语言、不替代交付 spec，也不更改产品术语或既有 ADR。
- 视觉与交互的既有权威来自 [ui-v1 设计稿](README.md)、相关界面稿及 token 文档；判据治理遵循 [ADR-0015](../../adr/0015-ux-quality-line-machine-criteria.md) 和 [判据目录说明](criteria/README.md)。
- 已有判据适用时关联原判据。新发现未被覆盖时保留观察证据与影响，按需提出判据提案；不把未裁定的审美意见直接标成已确认的“体验债”，也不因静态检查通过而抹去实操观察。
- 本文不修改冻结判据、阈值或签字文件。需要新增正式判据时遵循原有提案与生效流程。
- 延续 [术语表](../../../CONTEXT.md) 的边界：谱提供个人信息，藏不上 AI，底稿纯派生，沉淀写谱保留人工确认。
- 准备运行环境时遵循 [双实例手册](../../runbook/dual-instance.md) 与 [home 手册](../../runbook/home.md)；保留独立 home 和端口隔离，避免读写正式 DSH home。
- 历史验证、前次项目调查与本轮体验证据分别注明日期和来源。本文没有新增任何实测结论或用例统计。


## 9. 具体工具与执行方案（2026-11-02 补充）

当任务要求由 Agent 自主发现入口并自动重放、缩减异常时，使用[自动用户体验侦察与 Debug](自动用户体验侦察与Debug.md)。下文保留 2026-11-02 的实操工具计划及固定任务批次。

本节将前述流程落实到工具、入口、用例和证据。命令分为“已有，可在执行阶段运行”和“拟新增，尚不能运行”；本文更新不包含安装、启动或脚本实现。

### 9.1 工具选型与当前能力核对

采用 **Node.js + Playwright JavaScript API + 系统 Edge + 仓库既有 UX 判据**。浏览器实操由 AI 编写和执行任务脚本，并读取每个关键步骤的真实截图；动态探索后把稳定路径固化为脚本。首轮不新增 Figma、不更换组件库、不安装多个设计 skill，不将 Playwright Test Agents 或 MCP 服务作为前置。现有工程流程继续用于实现和代码复核。

| 用途 | 选定工具及入口 | 当前事实与处理 |
|---|---|---|
| 运行环境 | Node、pnpm | 本次只读查询得到 Node v22.18.0、pnpm 11.21.0；不等于应用已能启动 |
| 浏览器控制 | Playwright JS API，Edge channel `msedge` | 复用 `scripts/ux/collect/browser.mjs::resolvePlaywright()` 的解析方式；现有采集器使用全局 Playwright。当前安装可用性与 Edge 启动仍待执行阶段验证，不能沿用历史机器结论 |
| 隔离与启动 | `scripts/install-profile.mjs`、`scripts/isolation/startup.mjs` | 独立体验 home + 独立 web 端口；使用现有启动器，不自行拼 DSH 启动命令 |
| 机器判据检查 | `scripts/verify-ux.mjs` | 保留冻结判据、静态和浏览器检查；使用独立报告目录区分静态、修前与修后 |
| 实操与视觉证据 | 拟新增 `scripts/experience/run.mjs` | 在持久体验实例上走任务，保存截图、步骤、trace 和错误；不改变原巡检的职责与权限 |
| 功能与工程验证 | Vitest、`pnpm verify:all` | 按受影响业务选择测试；交付前执行工程检查，保留已知红归属 |
| 主观视觉复核 | AI 读取截图，用户判断未定的视觉取舍 | 按既有界面稿逐项给出位置、理由和前后效果；不以 AI 自评总分作为通过标准 |

源码核对揭示的能力边界：

- `browser-scripts.mjs` 现有剧本为 `create-pu`、`ask-consult`、`register-cang`，包含各自声明的场景，不能据此声称覆盖全部产品。
- `collectBrowser()` 使用临时 home、1280×900 窗口，结束后清理实例；适合固定巡检，不适合保留跨轮问事历史和人工复看。
- 当前采集器没有截图或 trace 落盘；它返回 `steps`，但 `runVerifyUx()` 未将该字段写入最终报告。现有报告不能充当完整实操证据包。
- 现有部分剧本使用 `force: true`，藏库异常场景还会构造坏注册表。新实操 runner 不沿用这些绕过方式来证明真实操作可达或真实服务成功。
- `verify:ux` 退出码 0 表示工具跑完，仍可能包含红项、未采到或浏览器不可用；必须检查报告内容。

以上是本次源码核对结果，不是本轮产品实测结果。

逐步检查退出状态，失败时停在对应步骤，不将整段无条件串行跑完。浏览器基准巡检在持久体验实例启动之前单独完成，避免共享 profile 配置写入相互覆盖。

具体前置与处置：

1. `--skip-install` 仅在仓库 profile 依赖已齐备时使用；缺依赖时按 home/双实例手册安装，再重新 doctor，不把“目录已建立”当成安装成功。
2. Playwright 解析失败时，先检查现有局部及全局安装；确实缺失才安装 Playwright 并记录所用版本。Edge channel 无法启动时记录准确报错，再决定修复浏览器环境；不默认下载 Chromium。
3. 使用虚构身份“体验用户-01”：出生日期 1990-06-15、当地时间 12:00、城市上海，其他必填项沿真实表单明确记录。谱名“体验-木工”，材料“我周末学习木工，希望安排练习时间”；不涉及真实个人数据。
4. AI provider/model 通过体验实例的真实设置入口配置。不能从日常 home 复制整份凭据或存储；使用专用测试配置。缺配置时先走无模型状态用例，正常问事与 AI 建谱明确记为阻塞。
5. horosa 通过现有生命周期入口启动或检查；只对实例实际连接的端点取证，不因端口空闲或 doctor 退出 0 就认定它可用。
6. 启动器输出的带 token 地址仅用于认证握手，不写进共享报告。先确认进入正确实例，再由界面完成出生信息、谱和问事等操作。
7. 每轮记录源码 SHA、工作区差异、客户端产物 SHA256、判据版本、实际 home、端口、Playwright/Edge 版本和服务状态。运行前后检查 `profile/cordis.patch.yml`；共享 link profile 可能被首跑改写，保留原始快照并只还原本次运行引入的变动。
8. 改源码后先停止本次实例，重建客户端并向同一体验 home 同步自有包，再启动复测；不能只刷新浏览器。相关启动与 home 规则继续以 §8 链接的 runbook 为正文来源。

### 9.3 最小补充工具：独立实操 runner

拟新增文件仅负责实操证据，不复制判据引擎：

| 拟新增文件 | 具体职责 |
|---|---|
| `scripts/experience/run.mjs` | CLI、连接指定体验实例、检查 home 与端口、启动 Edge、记录环境、执行场景并在失败时落盘 |
| `scripts/experience/scenarios/consult.mjs` | §9.4 的问事与历史回看场景 |
| `scripts/experience/evidence.mjs` | 统一截图、步骤 JSONL、浏览器错误、trace、脱敏与汇总 |
| 后续同目录的业务场景文件 | 按 §9.5 的顺序增加，复用同一证据记录器 |

拟定接口如下，**脚本尚未实现，这些不是已有命令**：

```text
node scripts/experience/run.mjs --home .experience-home/round-01 --port 19488 --scenario consult-normal --out ux-reports/experience-round-01/task-before
node scripts/experience/run.mjs --home .experience-home/round-01 --port 19488 --scenario consult-history --out ux-reports/experience-round-01/task-before
```

实现约束：

- 连接用户指定的持久体验实例；复用已核实的 token/cookie 握手方式，认证材料放在证据目录外的本地文件，由 runner 读取。URL、日志、trace 可能包含凭据，原始 trace 仅本地保存，分享前脱敏核查。
- 默认 Edge、1280×900、light；主路径再用 1024×768 检查窗口缩小、1280×900 dark 检查主题。尺寸是本轮采样条件，不新增设计断点。
- 使用角色、label、现有 `data-xuanshu-*` 属性定位。等待可见状态或明确业务终态；一般操作最多等待 15 秒，AI 终态预算 120 秒，超时保存当前画面和步骤，记“超时未完成”。执行期间持续报告正在等待的步骤。
- 实操不使用强制点击、内部 API 代替表单提交、直接改业务数据或模拟 AI 成功。错误输入、取消和离开通过真实控件触发；必要的故障注入另列诊断场景，不混入正常任务通过结论。
- 每个关键步骤保存当前 viewport 截图，必要时另存 full-page 图；开始操作前开启 Playwright `context.tracing`，场景结束及失败时保存 trace。捕获 `console.error`、`pageerror`、`requestfailed` 与 HTTP 4xx/5xx，过滤或脱敏请求中的认证信息。
- 一条场景失败只终止依赖它的步骤。独立场景继续，依赖场景记 blocked；不得在上一步失败后通过补数据“接着跑通”。
- 持久实例由启动器所属会话管理；runner 退出只关闭自身浏览器，不杀占端口的任意进程、不删除体验 home。

证据目录固定为：

```text
ux-reports/experience-round-01/
  static-before/                 # 已有静态巡检产物
  ux-before/                     # 已有浏览器巡检产物
  task-before/
    environment.json
    coverage.json                # caseId、状态、前置、最后成功步骤、证据路径
    findings.md                  # §6 的记录格式，编号 EXP-001 起
    consult-normal/
      steps.jsonl
      01-entry.png
      02-input.png
      03-pending.png
      04-result.png
      errors.json
      trace.zip
  task-after/                    # 相同场景与截图命名，便于逐项比较
  ux-after/
  batch-01.md                    # 发现编号、改动、逐项验收、遗留项
```

`coverage.json` 的状态限定为 passed / failed / blocked / not-run / needs-human；每条必须指向证据或阻塞理由。目录示例不是已有产物；实际只创建执行到的文件，不能提前填通过。原始报告与截图不入库，需长期留档的脱敏总结按仓库文档约定另行整理。清理前先读并行实现手册的 junction 安全流程，不在 runner 中自动递归删除。

### 9.4 第一批必须执行的具体用例

| ID / 拟定场景名 | 输入与操作 | 观察与验收 |
|---|---|---|
| E01 / `consult-no-model` | 空体验 home 完成必要首跑操作，未配置模型时打开问事并尝试开始 | 提示是否说明缺什么、配置入口是否可达；无假成功、无永久转圈。若产品禁止提交，则验禁用与解释，不强行点击 |
| E02 / `consult-empty` | 模型已配好，问题留空尝试提交 | 按实际规则阻止空提交、提示位置明确；不创建无意义会话 |
| E03 / `consult-normal` | 通过界面准备“体验-木工”谱，勾选它，输入“这周我只有两小时，怎样安排木工练习？”并提交 | 选择与输入正确带入，等待有反馈，真实 AI 产物可见；记录请求开始、首个反馈和终态时刻 |
| E04 / `consult-repeat` | 对可用提交按钮快速连续点击两次 | 不出现非预期重复会话或重复提交；界面有明确运行状态。以实际历史和界面结果核实 |
| E05 / `consult-return` | 输入未提交内容，切到自我总览，再回问事；对照已提交会话重复往返 | 记录是否保留草稿、谱选择、会话和阅读位置；与既有设计核对，规则未定的保留待判断，不擅自判错 |
| E06 / `consult-history` | 正常问事完成后离开，从真实历史入口找回，继续发送追问 | 找到同一条记录、原始输入和产物仍在、追问进入同一会话；返回落点合理 |
| E07 / `consult-restart` | 记录会话后通过启动器所属会话停止并重启同一体验 home，重新进入历史 | 原记录可找回、内容一致、可继续；认证重新握手，不能仅关闭浏览器冒充重启 |
| E08 / `consult-stop` | 真实响应进行时使用当前界面的停止入口，再继续操作 | 如有停止入口，检查终止反馈与后续可继续性；入口不存在时登记实际情况与规格依据，不伪造停止成功 |
| E09 / `consult-visual` | 用 E03/E06 的真实内容按 §9.3 的窗口与主题复看 | 检查标题/正文层级、主次按钮、间距、长文本、滚动、错误提示与弹层；每条发现标截图区域和既有设计依据 |

顺序为 E01 → 配置前置 → E02/E03 → E04/E05/E06/E08 → E07 → E09。需要新的会话时通过界面创建，不重用状态不明的上一次现场。正常服务不可用时，正常路径 blocked；可独立执行的错误输入、导航和视觉观察照实记录。
