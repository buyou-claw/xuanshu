# 实操体验评估：以完整用户任务为验收单位，证据先于结论

> 状态：accepted ｜ 日期：2026-11-02 ｜ 依据 `docs/design/ui-v1/实操体验评估计划-2026-11-02.md`（用户定稿的计划，本 ADR 是它的工程落地形式）

计划回答了「为什么评估、评估什么、怎么记录」。本 ADR 只回答一件计划留给工程定的问题：**这套评估以什么形式存在于仓库里，它的证据怎么产生、怎么判定、怎么防止自证及格。**

**背景**：工程证据已经很多——功能票完成、单元测试通过、静态巡检转绿（判据集 17 条 / 7 族，`pnpm verify:ux`）。这些证据都不回答一个问题：**人从真实入口走一条完整任务，是不是顺畅、能懂、拿得到结果、回来还在。** 玄枢上一轮的真实反馈是「UI 丑，交互逻辑严重不人性化，问题很多，没办法一条一条列举」——判据线（ADR-0015）把「丑」拆成了可数的清单，但**任务能不能走完**始终没有载体。

**决定：新增一条实操评估线，以「一条完整用户任务」为验收单位；它产出的是证据与发现，不是结论；它不进入 `verify:all` 的门。本线以 ADR 形式存在，不新建 `docs/specs/`（ADR-0016 第 1 条）。**

具体定值：

1. **验收单位是任务，不是判据、不是屏**：一条任务从入口、输入、动作、等待与反馈，一直到结果、离开和再次找回。判据绿、单测绿、巡检绿各自只提供**部分**证据，都不能单独证明这条任务顺。任务清单见计划 §4（九条）与 §9.4（首批 E01–E09）。
2. **证据先于结论**：每个关键步骤落 viewport 截图 + `steps.jsonl` + `errors.json`；`context.tracing` 全程开启，场景结束或失败时存 `trace.zip`。**一张静态截图不能证明跳转、保存或重启后的行为**（计划 §6 末句）；因此每条发现必须携带「可复现步骤」而非只有图。
3. **不伪造闭环**：不使用强制点击（`force: true`）、不用内部 API 代替表单提交、不直接改业务数据、不模拟 AI 成功。错误输入、取消、离开**通过真实控件触发**。故障注入单列为诊断场景，**不混入正常任务的通过结论**。（既有 `browser-scripts.mjs` 的部分剧本用了 `force: true`，新的实操 runner **不沿用**这一绕过方式——那是为静态巡检取证，不是为证明「真实操作可达」。）
4. **runner 自己拉起实例，home 持久、进程随 runner 起停**：复用既有 `startIsolatedInstance`（spawn → 抓 `?token=` → 换 cookie → 结束还原 profile → 摘 junction 后再删目录）。**不新增「把 token 写盘」的常驻凭据文件**——那会制造一个跨进程可读的凭据，正是本线要防的东西。因此「持久」= **home 与数据跨轮复用**，不是进程长驻。E07「重启后找回」按此口径验：停旧进程、保 home、起新进程，再走历史入口。
5. **一套状态词表，两处消费**：`coverage.json` 的状态**复用判据判定词表**（`pass` / `fail` / `not-collected` / `blocked`），不另造 `passed` / `not-run` / `needs-human`。旧词映射：`passed→pass`、`failed→fail`、`not-run→not-collected`、`needs-human→human-only`。**「未采到 ≠ 通过」这条铁律只允许一份口径。**
6. **发现编号不是判据 id**：`EXP-001` 起递增，只用于发现登记与批次引用；**不进入判据集，不可被 `UX-FIX:` 引用**（`check-ux-fix-notes.mjs` 会把不存在的判据 id 判红——这条写清，否则会误伤修复说明）。发现若最终要机器判，走 ADR-0015 的提案 → `rules/` → 投影 → 签字流程，**不许**把 EXP 编号偷渡成判据 id。
7. **只测量，不判定审美**：视觉取舍集中呈现前后效果，留给人判断。AI **不自行修改冻结判据**，也不把未裁定的审美意见标成「体验债」（`CONTEXT.md` 的定义：没过判据的一律不算体验债，是待判定的判据缺口）。
8. **不进 `verify:all`**：与 ADR-0015 第 8 条同口径。本线的产物是报告与发现，不是断言。升级成门需另立 ADR。
9. **「切走再回来」有依据了**：计划 §9.4 E05 要验「未提交内容切走后是否保留」，但设计稿原先没写这条规则，评估者无从判定。已在 `docs/design/ui-v1/README.md` **§13** 定下：同面板内切走**保留**草稿/谱选择/阅读位置；跨会话切换**不保留**（防串味）；重启后**只保证已落盘会话**。**不新增判据**（无机器阈值），它是评估的判定依据。
10. **独立且不入库的环境**：`.experience-home/` 与 `ux-reports/experience-*/` 一律 gitignore（前者已加入）。使用虚构身份与虚构材料，不复制日常 home 的凭据。「环境准备完成」**不算**体验验证完成（计划 §5 第 2 条）。

**新增的 seam（只有一个）**：证据记录器（`scripts/experience/evidence.mjs` 一类）。它把「一次操作 → 一份证据」这件事做成可测的纯结构：截图落点、`steps.jsonl` 行形状、`errors.json` 的捕获与脱敏、`coverage.json` 的状态闭集。**它能用临时目录零浏览器测**——照 `tests/ux/family-dc.test.mjs` 的「录制夹具走同一条判定路径」范式。浏览器侧不新增基础设施：起实例、握手、清理全部复用既有 seam，端到端只留 1 条。

**Considered Options**（都不选，理由记下来）：

- **把实操评估写成 spec 04 放 `docs/specs/`** —— 破 ADR-0016 第 1 条（`docs/specs/` 已整目录删除，规格与代码分叉是本仓已偿过的债）。本线是**决策 + 可执行约束**，正是 ADR 与测试的形态。
- **让 runner 连人起的持久实例、token 落盘共享** —— 需要新开一条「凭据写盘」通道；持久实例的 `?token=` 打在启动器 stdout 上、不落盘，跨进程拿不到。落盘则制造常驻凭据文件，与本线要求的「认证材料放证据目录外、分享前脱敏」相悖。
- **runner 由人手工粘贴 `--url`** —— 每次执行绑人手，与计划「AI 主动探索、不要求用户逐个口述」的目标相反。
- **复用 `collectBrowser()` 的临时 home 做实操** —— 它结束后清理实例（`stop()` 删 home），跨轮问事历史与人工复看都没有；适合固定巡检，不适合这条线。
- **另造一套 `passed/failed/blocked/not-run/needs-human` 状态词表** —— 与判据词表并存，「未采到 ≠ 通过」会出现第二份口径，两边迟早各说各话。
- **把实操评估升级成 `verify:all` 的门** —— 误报未清零就挡门，等于教人绕过（同 ADR-0015 第 8 条否决理由）。
- **给未提交草稿做持久化** —— 引出草稿与谱选择的一致性、清理、隐私三个新问题（输入常是要紧事，落盘就进备份面）。本轮不做，登记为已知边界。

**Consequences**：

- 新增：`scripts/experience/`（runner + 场景 + 证据记录器）、`ux-reports/experience-<轮次>/`（gitignore 产物）、`.experience-home/`（gitignore 环境）、`docs/design/ui-v1/README.md` §13（切走保留规则）。
- **首轮范围**：E01–E09（问事与历史回看这一条样板路径），顺序见计划 §9.4。这条路径被选中是因为它同时压到入口辨识、重复信息、等待反馈、返回落点、结果保留与视觉一致性——**一个问题最密集的路径先用**。
- 后续批次 A–F（批次上限 5 项发现/批，计划 §9.5）逐轮推进；每批交付 `batch-NN.md`：修了哪些 EXP、原因是否已证实、修改范围、原步骤复测、前后截图、测试与工程检查、继承红、阻塞与待人工判断。
- **转绿工具的实际限制要如实说**：`scripts/ux/regreen.mjs` 检查修前报告**全部** fail，没有「只选本批发现」的参数。所以批次验收口径是：逐条记录本批「判据 ID × 界面面」的 before/after，并核对完整报告里的新增回退；**本批未涉及的继承红单列**，不阻止如实报告局部修复，但**不能宣称全局转绿**。
- **修复成本口径**：本线本身**不写业务代码**。发现 → 修复是另一阶段（计划 §5.1 的「实施小批修复」），修复仍受 ADR-0015 判据约束与本仓既有验证要求（`pnpm verify:all`）。
- 与既有 `verify:ux` 的**分工**必须写进报告：`verify:ux` 读源码/计算样式（静态 + 固定剧本），本线读**真实操作序列与截图**。静态扫描测不出的四类问题（控件没边框、数字差一小时没解释、点了没动静、过时状态断言）只有本线能发现——这也是 `verify:live` 已经验证过的方向。
- **实证边界**：桌面壳的真实窗口 / 托盘 / 通知 / 自启，浏览器替代不了，按 shell 手册另测并单独登记缺口（计划 §4 末、§9.5 F 批）。
**裁决记录（2026-11-03）：口径统一与「未验项」的处置。**

- **空手开会话（EXP-002）**：设计稿 `S6 §6 empty`（「谱都非必填；你可以先空手问一句」）与界面现文案（「说事（可先空手开一个会话）」）都允许空手开会话，而票 #79 的验收标准写「不创建无意义会话」——同一行为被要求成相反两件事。**裁决以设计稿为准：空手开会话允许，票面那句话作废**（设计稿 §6 已同步写明这条裁定与其两条要求）。于是 E02 的失败点不再是「不该建」，而是「建了之后进不去（EXP-001）＋ 玄枢界面没有删除入口（`consult-views.tsx:391` 置灰，契约未冻结删除 RPC；DSH 原生会话面板能否删**未验**）」。要补的是可回收与去向，**不是**给输入框加门禁。
- **未验项的处置**：按「是不是硬性缺陷」分两类。**非缺陷、暂时接受**（不再当欠账）：本机造不出的现场（`no-edge` / 启动被拒）、产品未出现的分支（禁用提交 / 永久转圈 / 超时）、真实内容里不存在的形态（不可断长串的省略号分支）、不在本票检查面的项（键盘焦点 N-003、桌面壳、dark × 1024 组合、填八字与 horosa 前置）。**仍算缺陷、已登记待修**：EXP-001（进不去会话）、EXP-004（终态提示在视口外）、EXP-005（列表标题陈旧）、EXP-008（切走丢草稿）。`task-after` 与跨会话 composer 层面的串味属修复阶段 / 本轮范围外。
